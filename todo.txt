recently added
--------------
 * ff4 snes (u) ("Final Fantasy II (USA)"): monster / boss / summon graphics
   are now editable - the opaque monsterGraphics blob became 90 pointer-
   deduplicated graphics objects with per-object size (monsterSize table, or
   the boss properties record for bosses), format (snes3bpp/snes4bpp from the
   is3bpp flag) and palette (3bpp = first 8 colors of monsterPalette[p];
   4bpp = p + p+1 composed); every object and palette is named from the ROM's
   own monster names, bosses marked with *
 * ff4 snes (u): the graphics region is fragmented in the ROM (bank 0d
   interleaves monster pools with map/npc/portrait/window palettes), so the
   array is fragmented with capped static itemRanges - every byte has exactly
   one owner; graphics pointers for this game are linear in FILE space, which
   needed the new "isMapped": false pointerObject option in romtools.js
 * ff4 snes (u): battle editor and VRAM viewer updated to resolve
   graphicsPointer.target (with a fallback so the FF4 J blob definition keeps
   working); Monster/Battle tree sections now expose the graphics, the
   properties tables and the palettes
 * romtools: sizeFrom accepts a list of specs with condition/indexProp
   indirection/sizeIndexProp/noSize/formatProp+formats/linkPalette.indexProp;
   itemRanges can combine with pointerObject; fragmented items get definition-
   space ranges (fixes latent double-mapping outside GBA)
 * graphics view: objects with no format no longer crash selectObject
 * new tests: ff4-sfc-xcheck.js (pointer resolution, one-owner rule, decode
   parity vs an independent decoder, palette pins, paint + byte-exact undo),
   ff4-sfc-app-test.js (browser: paint, boss pool, 4bpp compose, battle VRAM),
   ff4-sfc-names.py (generates the whole model from the ROM), app-shots.js
   (generic screenshot tool)
 * in-app graphics painting: pencil, flood fill, eyedropper (tool menu, keys
   V/B/G/I, right-click is always the eyedropper), copy/paste with a movable
   floating layer, Delete to clear a selection, middle-click pan, wheel zoom
   anchored at the cursor, image-bounds and tile-grid overlays
 * in-app palette colour editing (double-click / right-click a swatch)
 * ff5 advance (u/e): monster graphics and monster palettes are now editable
   (Battle -> Monster Graphics / Monster Palettes), named per monster
 * ff3 nes (j): monster graphics are editable - six fixed-size classes (4x4,
   4x6, 6x6, 6x6, 6x12, 12x6) selected by bits 5-7 (size) and bits 0-4 (index)
   of $2E:$8B00, plus the monster graphics properties table, the 256 battle
   palettes (new nesFixedPalette format: colour 0 is always black), battle
   character graphics for all 24 jobs and the toad/mini graphics
 * ff3 nes (j): every monster graphic is named after the monsters that use it,
   every battle palette after the battle groups that use it, and every
   character block after its job - names generated from the ROM itself
 * ff3 nes (j): battle background, summon, battle sprite, map sprite and attack
   graphics are now visible as raw 2bpp banks
 * ff3 nes (j): fixed worldPalette, which pointed into the world tileset data
   (world maps use mapPaletteBase, see 3A/9091)
 * ff3 nes (u): the English translation got the same battle graphics (its
   graphics data is byte-identical to the Japanese dump - only the text banks
   differ), labelled with the ROM's own English monster and job names
 * ff3 nes (u): added patches/ff3u-nes-fix-dump.ips for the mislabelled
   English dump (header-only difference, mapper 132 vs 4)
 * ff3 nes: each monster graphic now defaults to the palette its own battle
   groups use (new generic itemPalettes key on ROMArray; 86 distinct defaults
   across the 96 graphics), and each job's character graphics default to that
   job's sprite palette ($FC-$FE)
 * ff3 nes: battle character graphics are shown two tiles wide, matching the
   game's 2x3 sprite grid, instead of scrambling every pose across 14 columns
 * ff3 nes: boss graphics - the pointer table and 24 tilemaps (18x12 tile ids
   that index the shared monster tile pool), rendered in the app via a new
   "whole": true tile-pool option in the graphics view
 * ff3 nes: monster, character, boss and summon graphics are now transparent
   (no black box around the sprites)
 * ff3 nes: a monster graphic opens with BOTH of its battle palettes shown at
   once (new "compose"/"offset"/"name" palette definition keys - the panel
   shows two rows and clicking a row flips the sprite between them), and the
   palette dropdown leads with the palettes of the monsters that actually use
   the selected graphic, named after them
 * ff3 nes: summon graphics - the summonProperties table ($2A:$9440) and eight
   summon tilemaps with a dedicated ff3SummonTilemap format (6-bit tile index,
   0xff = empty), each with its three sprite palettes; Bahamut and friends now
   render as whole creatures
 * ff3 nes: boss tilemaps use a dedicated ff3BossTilemap format (0x70-0xff =
   the boss's 144 tiles) and scope the graphics pool to just that boss, so the
   tilemap and the pool panel agree; bosses also get two named palettes
 * ff3 nes: black is opaque again - colour 0 is the sprite outline in the ROM,
   so the earlier "make it transparent" change deleted outlines as well as the
   box (the box is real: monsters are rectangles of BG tiles, index 0 = black)
 * ff3 nes: both battle palettes now show at once, per 2x2 tile cell, from the
   ROM's monster attribute data ($2E:$8F20) - new generic itemAttributes key on
   ROMArray plus per-tile palette bits in the graphics view; Mandrake gets its
   brown body and green leaves in one image
 * ff3 nes: editing a palette colour actually changes the ROM now - a composed
   palette spans several ROM palette objects, so edits are routed through
   paletteSegments/targetForColor instead of always hitting the last one loaded
 * ff3 nes: fixed 12 boss tilemaps that pointed at the wrong graphics - a boss
   pointer addresses a 16 KiB window, so those pools sit in the unused stretch
   after the size-class arrays (new monsterGraphicsSpare assembly)
 * ff3 nes: summon tilemaps decode bits 6-7 of each cell as the tile's palette,
   so summons render with all three of their sprite palettes at once (Bahamut
   is a proper multi-coloured dragon)
 * ff3 nes: fixed Up/Down arrow keys, which stopped moving the tree selection
   because opening a graphic focuses the graphics pane and the arrow handler
   lived only on the left pane
 * ff3 nes: labels now list boss monsters first with a * marker - of 127 named
   boss monsters only 32 use the tilemap mechanism, the other 95 live in the
   ordinary size-class arrays
 * ff3 nes: fixed the per-cell palette split, which was wrong three ways: the
   record index is (props & $1F) + a per-class offset (2F/A0E7), not props &
   $3F, so 48 of the 96 graphics read the wrong record; the cell walk is over
   the formation slot, so a 4x4 monster's cells are bits 2-5 of its record
   (that was the "half line" on Firefry/Liliput); and $2E:$8F00 inverts the
   cells for every monster id $80-$FF, which is why bosses look swapped
 * ff3 nes: bosses have per-cell palettes too - 7 bytes per tilemap index at
   $2E:$8FC0 (2F/A820), 9x6 cells for the 18x12 map; Medusa, Harpy, Bahamut
   and Odin now render with both battle palettes
 * ff3 nes: the two attribute tables are real assemblies (monsterAttributeData
   $2E8F00-$2E8FC0, bossAttributeData $2E8FC0-$2E9028), named byte by byte, and
   the views read them live - editing a byte repaints the monster; both views
   gained a "Swap palette cells" control for graphics shared with a boss
 * ff3 nes: editing boss graphics works: "Place tile" is on by default for
   pool-based tilemaps, painting the pool panel writes through to the assembly
   that owns those bytes (saveGraphics used to bail out on a whole-array pool),
   and the Tool menu appears for pools - map tilesets stay read-only
 * ff3 nes: ff3BossTilemap keeps a background cell as 0x100|byte instead of
   collapsing it to 0, so editing one cell no longer rewrites the other 3798
   background cells of the battle (3F/F90A copies all 216 bytes)
 * ff3 nes: every monster name now appears in the label of its graphic (the
   "+N" truncation made 149 monsters, many of them bosses, look missing)
 * ff3 nes: new tools/ff3-nes-attrcheck.py re-derives the palette-cell model
   from the ROM and scores it against videogamesprites.net rips against the
   wrong variants: 61/62 agree at 100%, and the model wins every case where a
   wrong record index or slot alignment would change the answer
 * ff3 nes: guarded ff3-map.js changeLayer('showRooms'), which dereferenced a
   mapPalette assembly FF3 never had
 * ff3 nes: NEW - paint the palette cells: Tool > "Palette cells" (key C) on a
   monster, "Paint palette cells" on a boss layout; pick a palette row in the
   panel, click or drag the cells, and the bit is written back to
   monsterAttributeData / bossAttributeData (undoing the per-monster inversion)
 * ff3 nes: NEW - every palette pair a monster's battles use is in the palette
   dropdown as its own composed entry (Dark Cloud's three forms, a monster and
   its boss): [[pal1,pal2], [pal1,pal2], ..., battlePalettes], 88 of 96
   graphics offer more than one
 * ff3 nes: fixed "bosses are not editable" - mouseDown never moved
   selection.x/y for the left button, so a stamp painted the cell under the
   *previous* click instead of the one you made
 * ff3 nes: fixed garbled Odin and Leviathan - bit 5 of the boss pointer means
   "summon graphics, flipped", and the ROM stores those two tilemaps
   right-to-left; "mirrorX" mirrors layout + tile pixels for display and
   un-mirrors on save (ROM stays byte-exact)
 * ff3 nes: picking a single tile in a boss's pool panel now also arms the stamp,
   so it is click-tile-then-click-place rather than right-click-then-left-click
 * ff3 nes: Up/Down now move the tree from the boss layout pane too (it takes
   focus, and the arrow handler only lived on the left pane)
 * ff3 nes: fixed the invert-bit reading - 2F/A133-2F/A141 ASLs the byte inside
   the loop and only then tests bit 7, so the flag is bit (6-(id&7)) of byte
   (id>>3) and always 0 when id&7==7: 112 of the 128 boss ids invert, not 128.
   That is why Cyclops ($97) and Ouroboros ($9F) looked wrong
 * ff3 nes: new tools/ff3-nes-palcheck.py verifies every monster and boss
   against reference rips: it first learns the rip site's NES palette from the
   rips themselves (our colours and theirs never match numerically), then scores
   the model against the swapped-pair and un-inverted alternatives. 27 of 36
   rips exact; 6 boss ids disagree with the rips and the ROM wins by default,
   with the reversed pair offered in the palette dropdown
 * ff3 nes: the palette dropdown now lists every pair a monster's battles use
   AND its reverse ("... #243, swapped"), so flipping which palette is "first"
   is one click - no "Swap palette cells" toggle, which is removed
 * ff3 nes: clicking a palette row no longer recolours the whole sprite; with
   per-cell palette bits the base colour offset is 0 and the row only says what
   painting writes
 * ff3 nes: the boss/summon pool panel now shows the tiles in the order the
   tilemap uses them ("followLayout"), so Odin and Leviathan read as a knight
   and a serpent there too instead of noise, and Pencil/Fill paint the part you
   see; ROMGraphicsView.tileOffset resolves through that layout
 * ff3 nes: the boss toolbox now really offers Pencil / Fill / Colour picker
   for the tile pool (the shared #edit-controls bar meant the graphics view's
   Tool menu was never built)
 * ff3 nes: removed the "Colour 0 transparent" toggle - index 0 is the outline
   colour, so it only ever deleted outlines
 * ff3 nes: BOSSSES ARE PAINTABLE LIKE MONSTERS - the boss layout pane gets a
   Tool menu (Select / Pencil / Fill / Colour picker) that paints pixels into
   the pool tile occupying the cell under the cursor (paintLayoutDown/Drag/Up
   -> graphicsView.paintPixel/floodFill/pickColor, mapped through poolLayout in
   ROMGraphicsView.tileOffset). "Place tile" is just a checkbox for Select now,
   and the pool panel no longer adds a duplicate Tool menu
 * ff3 nes: fixed the mirrored bosses properly - 3F/F90A copies the boss
   tilemap as stored and 3F/F94F+3F/F970 flip each tile's PIXELS ($92 = use
   horizontal flip table), so mirrorX must only set the per-tile flip bit;
   reversing the columns too mirrored twice and left Odin/Leviathan scrambled
   in the layout while the pool panel looked right
 * ff3 nes: the pool panel follows the tilemap layout ("followLayout" +
   syncPoolLayout) and shares its per-cell palette bits (cellsObject), so the
   layout and the pool panel now show the same creature in the same colours
 * ff3 nes: SEPARATED the two jobs into the tree, as asked - "Boss Tilemaps" /
   "Summon Tilemaps" are placement (Place tile + Paint palette cells, no Tool
   menu), and "Boss Graphics" / "Summon Graphics" are 24 + 8 new entries that
   open in the ordinary graphics editor with Select / Pencil / Fill / Colour
   picker / Palette cells, exactly like a monster graphic
 * ff3 nes: new "window" assembly in rom/romtools.js - a graphics object that
   reads a slice of another assembly's decoded bytes and writes through to it,
   but never owns bytes (no range, assemble() returns early), so the one-owner
   rule still holds and the xcheck overlap test ignores it
 * ff3 nes: "layoutFrom" makes a window display its tiles in the order the
   tilemap places them, so Boss Graphics 22 is a paintable bitmap of Odin
   rather than a sheet of loose pieces; tileOffset() resolves through
   poolLayout so the painted pixel lands on the right tile
 * ff3 nes: fixed the boss palettes - the $2E:$8F00 invert flag must NOT be
   applied (all 24 boss tilemaps and all 8 boss ids with rips render correctly
   un-inverted; ff3-nes-palcheck went 25/36 exact -> 33/36, with 0 cases
   preferring the swap or the inversion). It is recorded behind
   APPLY_INVERT_FLAG = False
 * ff3 nes: fixed boss pool ranges running past the end of their container
   (poolBytes ignored the clamp), which made some boss windows read garbage
 * ff3 nes: fixed the black/garbled boss graphics windows - a ROMArray's own
   .data is still the ENCODED planes, so a window onto a size-class array must
   read the concatenation of its items' decoded data (windowSourceBytes), and
   replaceData must split the write across those items. That is why Big Rat,
   Jin, Ninja, Kunoichi, GutzCo, General, Kraken, Land Turtle and Cerberus were
   broken while the spare-region bosses were fine
 * ff3 nes: a window now re-reads its source when the source changes (it
   observes the owner and each of its items) - an undo notifies the owner, so
   the window copy was going stale
 * ff3 nes: the window's tile flip comes from the tilemap object's mirrorX, not
   from the stored words (the ROM never carries a flip bit) - that was the
   "same jumbled problem" on Odin and Leviathan
 * ff3 nes: the app test now compares all 24 boss + 8 summon graphics windows
   byte-for-byte against the pool bytes the tilemap path reads, and fails any
   that are all black
 * ff3 nes: PALETTE PAINTING, the final shape - the palette row you have
   selected is applied to the 2x2 cell you touch, live, as part of the same
   pencil or fill gesture; the "Palette cells" tool does it without touching a
   pixel; the color picker selects the row the clicked cell uses
 * ff3 nes: fixed "pencil only updates on mouse-up" - writing an attribute byte
   does not repaint anything, because the palette per tile is baked into
   this.tilemap by updateTilemap(); added refreshPaletteCells()
 * ff3 nes: fixed "nothing happens when I paint a pixel that already has that
   index" - paintPixel and floodFill used to early-return when the index was
   unchanged, but the cell still had to move palette rows
 * ff3 nes: fixed cell addressing - attributeCellForTile() takes TILE
   coordinates and the graphics view has pixels, so writes landed past the end
   of the record and silently did nothing; added attributeCellForPixel()
 * ff3 nes: fixed color picking on boss windows "picking transparency" -
   ROMGraphics had the attributeRef block twice in its constructor and the
   second copy overwrote attributeCells with undefined; also pickColor was
   folding the palette row into the color index, putting it out of range
 * ff3 nes: fixed undo/redo looking dead - a stroke released outside the canvas
   left the action group unclosed and `painting` stuck true, which blocked
   every reload; finishStroke() now runs from the canvas mouseup and a
   document-level safety net (same for the tilemap's palette-cell strokes)
 * ff3 nes: the eyedropper cursor now tints with the selected palette row
 * ff3 nes: summon tilemaps render correctly again - a graphics "range" already
   starts at the summon's block, so the definition's tileOffset must be 0
 * ff3 nes: importing into a boss/summon window maps through the tile layout
   instead of copying linearly (a linear copy garbled the image)
 * ff3 nes: the browser tests now run in a fresh Chrome profile
   (--user-data-dir + --disk-cache-size=1) so a cached JS/JSON can never make a
   test lie about the current code
 * byte-exact undo: re-encoding is skipped when decoded data matches what was
   loaded, and unchanged-size assemblies are no longer relocated
 * navigator: Up/Down move the selection and expand the next section; fixed
   leaf rows never highlighting because selectObject() indexed into a row's
   child nodes
 * new tests: ff3-nes-xcheck.js (range overlaps, decode parity, palette round
   trip, edit lands on the right bytes, byte-exact undo), ff3-nes-shots.js,
   ff3-nes-dump.py (render any region straight from the ROM),
   ff3-nes-names.py / ff3-nes-add-graphics.py

game specific

   boss means editing the tiles in the size-class arrays; a per-boss "which
   tiles does this boss use" highlight in the class arrays would help
 * ff3 nes (j/u): boss tilemaps are single-palette in the game (the class-6
   attribute path in 2F/A86C reads past the 6-entry class table, so there is no
   per-cell data to reproduce) - both palettes are loaded but not mixed per cell
 * ff3 nes (j/u): blank cells in boss/summon tilemaps normalise on save (a
   boss's background cells all write back as 0x00) because the decoded tilemap
   word cannot remember which background tile was underneath

   definition does not define (only reachable from the unwired showRooms
   control)

   view cannot select palettes from it
